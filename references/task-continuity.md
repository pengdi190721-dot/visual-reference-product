# 需求不丢失与修改接续

这是助手内部工作记录，不让学员填写表格、背口令或逐步批准。目的不是增加问答，而是让已经说过的话持续生效。初次逐图解析继续直接做；进入设计前建立清单，续作先读当前清单。

## 单一有效版本

在独立任务目录复制 [需求模板](../templates/task.json) 为 `task-v001.json`。模板刻意留空来源，不能原样通过检查。每次用户增加要求、确认参数、指出缺陷后保存下一版，旧版只读；`previous.path` 和 `previous.sha256` 指向上一版文件及真实散列。`流程状态.md` 只保留当前摘要和最新版文件位置，历史另存；不得不断追加互相矛盾的“当前状态”。

清单中必须有：

- `questions`：产品信息与用途/风格问题分开。产品项编号固定为 `product`。`unasked` 尚未问、`waiting` 等待回复、`answered` 已答、`skipped` 用户明确跳过、`deferred` 用户已要求先出草稿、`not_applicable` 不涉及产品信息。后者写原因。已答/跳过/先出草稿写 `basis.ref` 对应消息位置、`basis.quote` 对应用户原话；不能把“彩色版式”作为“不要问参数”的证据。
- `outputs`：每个约定成品单独编号，写页型、比例和用途。如三屏分别 O01/O02/O03；单页含三幅细节图仍是一页。用户改为一张高密度图文页时，保留旧编号但标 `retired`，用新的编号记录新交付。不能一边说换成单页、一边继续按旧三屏汇报。
- `requirements`：本次真正要落实的产品/人物锁、关键视觉关系、准确中文文案、用户明确喜欢的元素，以及未解决缺陷。每项有固定编号、来源、关联输出、依赖素材、具体落实方法。用户圈出的重点分别登记，不能只写“更可爱”。用户未要求的所有装饰不必机械加入。
- `changes`：改动已有需求内容、状态、素材依赖或交付规格，必须按编号记录用户更正/改变方向的原话与位置。方案内部位置微调可只改 `implementation`，但不能借此删除或违背 `text`。新增要求追加编号，不能覆盖旧编号；已取消也保留记录。

`source` 同样包含 `ref` 和 `quote`。来源可以是用户消息、图像证据编号及明确观察、或本次明确采用的设计决定；不要编造用户原话。变更记录必须对应真实用户修正/授权，不能引用自己的“我认为这样更好”。已知产品事实作为 `identity` 或 `copy` 条目写入，新增用户确认后同步所有派生文案；旧“未知”移入历史，不得重新询问。参数彼此明显冲突时集中确认该冲突，不自行改成另一个值。

清单是当前有效约定，产品档案、蓝图、提示词、详情核对单和验收报告都引用同一版本。不能只改其中一个文件。发现旧文件冲突，先依据最新用户消息修正；不要以旧档案否定新确认。

## 两道实际检查

设计调用使用第 3 版 `job.json`，新增 `contract` 指向当前清单，`output_ids` 指向本次任务负责的成品。本次可只执行其中一页或一个制作阶段，但助手仍负责继续完整约定范围，不能把中间产物当整套交付。单独抠图为中间素材时为它分配输出编号，不能冒充最终整页。

```sh
python3 scripts/check_task.py /任务目录/task-v001.json
python3 scripts/meitu_adapter.py plan /任务目录/job.json
python3 scripts/meitu_adapter.py submit /任务目录/job.json --run-dir /任务目录/运行01
```

适配器会检查接续记录、问题收口、需求覆盖和依赖素材，并把本次有效需求自动附进实际发送的提示词。删了参考附件、漏了需求落实方法、篡改前版或没有用户跳过依据时不能直接提交。旧第 2 版调用计划须补建清单后迁移，不能降低版本绕过；旧房间查询仍沿用原记录，迁移不等于重发任务。

**所有路线都受同一清单约束。** 用网页排版、图片合成或其他本地方式补中文字时，也先检查清单、保留当前设计要求，不能因为不走适配器就省略验收。美图主通道不变，排版方式按成品效果选择；不宣称“生图一定排不好”“网页排版必然零错字”。

打开实际每张输出后填写 [交付报告](../templates/delivery.json)，绑定当前清单散列与各成图文件散列。每个有效需求必须有 `pass/fail/unverified` 和具体画面位置证据，不能凭提示词、原图来源或工具返回成功填写通过。新图片须重新检查，旧验收不能套到新文件上。

```sh
python3 scripts/check_task.py /任务目录/task-v001.json --delivery /任务目录/delivery.json
```

- `incomplete`：漏页、只完成底图、没看过成图、任一有效需求未通过。可以交阶段稿，但必须明确欠缺和下一步。
- `draft`：约定整套视觉已完成且逐项通过，仍有披露的创意详情/拟用文案待核实；在 `pending_details` 写具体位置与内容，关联详情核对单。
- `ready`：约定输出齐全、全部有效需求通过、没有待核实项。仍不能宣称“绝不会错”“百分百保真”。

已发现缺陷记录为 `repair` 需求，修订继承；只有实际新图通过相应检查，才能说已修复，不能通过删除该条来关闭。手写气质、装饰丰富度、主要构图等被用户明确指定时也属于有效需求，不得降成“只是审美建议”后宣布通过。纯粹内部建议先决定是否采用，未采用不要混成用户硬要求。

脚本只能拦住记录上的遗漏和矛盾，不能判断模型有没有伪造来源、照片是否漂亮或验收是否诚实。宿主如果绕过脚本直接调工具，仍可能漏项；因此每轮交付须同时给出简短覆盖结果，如“3/3 页已完成；气泡、手绘装饰、细节图均已核对；2 处补图待实物确认”。不能把测试通过说成实际成图通过。

## 本轮对话暴露的决策修正

1. **一次问清，别用另一个表单盖住产品问题。** 在同一次可回答交互中合并必要产品字段与用途，已知项不再问。仅答风格不等于跳过参数；若已经授权先出图，记“未答，先出草稿”并继续，不再强迫填全。不把没有回复当授权。
2. **页型与丰富度分开。** 小红书首图也可有细节图、人物、气泡和参数区；详情页也可以是一张完整图文页。根据参考和用户描述确定，不用“封面绝不能有细节”“详情必做多屏”的说法替用户选。
3. **执行已选完整范围。** 用户已选三屏并允许先出方案，不应做一屏就再次问做不做下一屏。授权范围内继续；仅真实业务交互、超出预算或必须用户决定的冲突才暂停。原图不足允许披露的创意补图，不能又要求“先补拍才能设计”。
4. **用户指定热闹，就设计有秩序的热闹。** 主人物与产品关系、错落细节、气泡、可爱手绘、跳色、标题力度一起设计；不能自行把复杂度压成商品网格。没必要固定为六个气泡，也不能规定最多两个。用大小、疏密、遮叠组织层级，别用删掉用户偏好的方式解决。
5. **圈选是更高优先级的视觉证据。** 每个圈说明“是什么、为什么喜欢、落到哪里、怎样验收”。页面上的爱心、太阳、四叶草与产品印花分开：可迁移装饰语言，不把别人的兔子印到用户的小熊产品上；将该趣味元素放到旁边，不因此删光可爱细节。
6. **局部修补保持整体。** 改标题边距时保留参考、人物关系、文案、装饰和细节区；修抠图不改身份。修完重新看全页。常规本地排版修复自行完成，别把每一处碰撞都变成学员的确认题；付费重试仍遵守已有授权与预算。
7. **不要用工具正确替代设计合格。** 纯原图贴入也可能裁错、失衡、糊边；排字也可能字体丑、字号错、元素挤压。用户问哪张好看，应直接比较焦点、空间、光线、层级与情绪，不用“我这张更真实”回避审美问题。
